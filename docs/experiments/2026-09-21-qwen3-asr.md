# Is Qwen3-ASR 0.6B fast enough to dictate with?

_2026-09-21, worktree branch off `4be5947` with sherpa-onnx 1.13.8. Intel
i7-9850H, 6 threads, CPU provider. **Every timing here was taken under heavy
load** — several agents were building on this machine and the load average
was 44–46 on twelve threads. Absolute timings are therefore far worse than a
user would see; the comparisons between models are sound, because each model
was measured in the same run, and they are what the conclusion rests on._

## Question

Qwen3-ASR is the one model in sherpa-onnx that biases toward a word list
without going through the beam search that is broken on Parakeet TDT: its
`hotwords` are a comma-separated string that lands in the decoder's system
prompt. Published evidence puts its 0.6B variant level with Parakeet v3 on
spontaneous accented speech under Silero VAD segmentation, spokenpad's own
architecture.

It is also a generative decoder, so the questions are: is it fast enough for
a push-to-talk release tail, how much memory does it take, does it invent
text on silence and on very short chunks, and what does it cost on the
author's own voice?

## Method

- Downloaded `sherpa-onnx-qwen3-asr-0.6B-int8-2026-03-25.tar.bz2` from the
  k2-fsa/sherpa-onnx `asr-models` release: **878 702 423 bytes**, sha256
  `393f8a14e2f5fb96746aaab342997a40641001fbd5bf9592a080a8329178ee96`.
- Wrote a `Family::Qwen3Asr` variant, a `Model::Qwen3Asr { language,
  vocabulary }`, one match arm in `shell/inference.rs`, and the per-family
  key validation. The patch is kept at
  `~/.cache/spokenpad-dev/models/qwen3-asr-family.patch` (138 added lines,
  32 removed, across `config.rs` and `inference.rs`); it is **not** in the
  repository, for the reason in the conclusion.
- `cargo run --release --example=eval` on the five local clips.
- A scratch harness (`examples/model_replay.rs`, not kept) measured decode
  time on 2 / 5 / 10 / 20 s slices, best of three; decoded digital silence of
  0.2 / 0.5 / 1 / 3 / 10 s and speech slices of 0.2 / 0.5 / 1 s; replayed
  captures through the VAD path counting empty and bare-"Yeah." decodes; and
  decoded the tail that Parakeet TDT beam search loses. Peak resident memory
  came from `/usr/bin/time -v` around the whole run.
- Decoded the release's own public `test_wavs/de.wav`, which ships a German
  reference, with the language detected and pinned to `de`.

## Data

- `eval-samples/*.wav`: five clips, 100 s, English dictated with a German
  accent.
- `~/.local/state/spokenpad/audio/`: the first 30 recovery captures for the
  replay, and the one capture whose tail TDT beam search loses. Private;
  counts only.
- `test_wavs/de.wav` from the release (public, 6.7 s, published reference).

## Results

### How the family has to be configured

Not like the others, and the differences are why it needs its own variant:

| | Qwen3-ASR |
|---|---|
| files | `conv_frontend.onnx`, `encoder.int8.onnx`, `decoder.int8.onnx`, and a `tokenizer/` **directory** holding `vocab.json`, `merges.txt`, `tokenizer_config.json` |
| `tokens` | must be the **empty string**; there is no `tokens.txt` |
| `vocabulary` | applies: one comma-separated string that sherpa-onnx splits, trims and joins with spaces into the system prompt `<\|im_start\|>system\n…<\|im_end\|>…`. A comma inside a phrase would split it, so the config rejects one. |
| `hotwords_score` | does not apply: nothing is scored per token. Rejected. |
| `decoding` | does not apply: there is no search to choose. Rejected. |
| `language` | applies, but as a **per-stream option**, not model configuration: `stream.set_option("language", …)` before each decode. |
| window | the decoder's `max_total_len` (512 by default) is shared by the prompt and the audio, at about 13 audio tokens per second, so a decode holds roughly 35 s minus whatever the vocabulary prompt costs. |

### Speed: about three times slower than the current default

Best of three on slices of `replacements-critique.wav`, a committed English
clip, with the three models run back to back under the same load. All three
returned comparable word counts on every slice, so nothing here is a decoder
loop that failed to run:

| audio | Parakeet TDT v3 greedy | parakeet-unified greedy | Qwen3-ASR | Qwen3-ASR ÷ TDT v3 |
|---|---|---|---|---|
| 2 s | 1.60 s (1.2×) | 1.59 s (1.3×) | 4.80 s (0.4×) | 3.0× |
| 5 s | 2.32 s (2.2×) | 4.13 s (1.2×) | 7.52 s (0.7×) | 3.2× |
| 10 s | 4.69 s (2.1×) | 4.05 s (2.5×) | 13.91 s (0.7×) | 3.0× |
| 20 s | 7.17 s (2.8×) | 7.64 s (2.6×) | 34.60 s (0.6×) | 4.8× |

Under this load Qwen3-ASR runs at **0.4–0.7× real time**, i.e. a decode takes
longer than the speech it decodes, while both Parakeets stay above 1×. It is
consistently **3–5× slower than the current default** on identical audio in
the same run.

On an idle machine `docs/asr.md` measures Parakeet TDT v3 at 0.22 s for 2 s
of audio, so that ratio puts Qwen3-ASR at an estimated **0.7 s** for the same
2 s tail — faster than real time, but roughly triple today's release latency
and above the low-hundreds-of-milliseconds budget a push-to-talk release has.
That last number is an extrapolation, not a measurement: the machine never
went idle. Everything else here is measured.

Setting a vocabulary makes it slower again, because the prompt grows and
shares the decoder's key-value budget with the audio.

### Memory

Peak resident set over a decode run:

| model | peak RSS |
|---|---|
| Parakeet TDT v3 | 1357 MB |
| parakeet-unified | 1398 MB |
| Qwen3-ASR, no vocabulary | 2532 MB |
| Qwen3-ASR, ten-word vocabulary | 2621 MB |

### Silence and very short chunks

| input | Parakeet TDT v3 | parakeet-unified | Qwen3-ASR | Qwen3-ASR + vocabulary |
|---|---|---|---|---|
| 0.2 s digital silence | `""` | `""` | `""` | `""` |
| 0.5 s | `""` | `""` | `""` | `""` |
| 1 s | `""` | `""` | `""` | `""` |
| 3 s | `""` | `""` | `""` | `""` |
| **10 s** | `""` | `""` | **`"提纲。"`** | `""` |
| 0.2 s of speech | `""` | `""` | `""` | — |
| 0.5 s of speech | 2 words | 1 word | 1 word | — |
| 1.0 s of speech | `""` | 2 words | 2 words | — |

Ten seconds of digital silence still produces a Chinese word on 1.13.8, with
no vocabulary set, and it reproduced on a second run hours later. The 1.13.7
fix (#3907) is specifically for the case where hotwords or a language **are**
set, and with a vocabulary the same input returns `""` — so the fix works and
the unguarded path is still open. In spokenpad this is guarded a second time:
the VAD gate means a decode is only fired on a window the detector called
speech. No model invented text on a short *speech* slice; the disagreements
in the last two rows are one or two words either way, which is what a
half-second of audio is worth.

### Accuracy on the five clips

| clip | TDT v3 greedy | parakeet-unified greedy | Qwen3-ASR |
|---|---|---|---|
| shell-commands | 51.7% | 34.5% | 58.6% |
| cd-home | 100.0% | 0.0% | 0.0% |
| keyboard-layout-reset | 21.1% | 0.0% | 21.1% |
| replacements-critique | 17.8% | 6.8% | 6.8% |
| new-model-review | 0.0% | 0.0% | 5.1% |
| **aggregate, VAD** | **18.7%** | **8.2%** | **15.9%** |

Better than the current default, clearly worse than the other candidate, on
this speaker.

### The tail, and the VAD replay: it loses nothing

The 10.6 s tail that Parakeet TDT beam search decodes to `""`: Qwen3-ASR
returns 8 words with the trailing silence and 8 without, taking 11.6 s and
10.3 s to do it — about one times real time under this load.

Replaying the first 30 captures through the VAD path — the same 53 chunks and
670 s of speech for every row:

| model | empty after padding | empty after the `Bare` retry | bare "Yeah." | words | replay speed |
|---|---|---|---|---|---|
| Parakeet TDT v3, greedy | 0 | 0 | 0 | 1088 | 2.0× |
| parakeet-unified, greedy | 1 | 1 | 0 | 993 | 2.2× |
| Qwen3-ASR | 0 | 0 | 0 | 1054 | 0.7× |
| Qwen3-ASR + ten-word vocabulary | 0 | 0 | 0 | 1053 | 0.8× |

Qwen3-ASR loses nothing, and the vocabulary prompt costs it nothing: one word
out of 1054. It sits between the two Parakeets on word count, where
`parakeet-unified` is already dropping content on this subset and drops far
more over the whole corpus.

### German, and English with a German accent

`test_wavs/de.wav`, against its published reference:

| model | output |
|---|---|
| Qwen3-ASR, language detected | exact |
| Qwen3-ASR, `language = "de"` | exact, identical |
| Parakeet TDT v3 | exact but for one hyphen and its case |
| parakeet-unified-en-0.6b | badly wrong: German transliterated into English words |

German is Qwen3-ASR's strongest showing and the only place it beats both
Parakeets. English with a German accent is the five-clip table above, where
it does not.

## Conclusion

**Not merged**, on four counts — but read the paragraph after them, because
the corpus replay changed the shape of this decision:

1. **Latency.** Under the load this machine was under, it decodes slower than
   real time. Scaled against the current default measured in the same run, a
   2 s release tail costs about 0.6 s where Parakeet costs 0.22 s — over the
   budget a push-to-talk release has.
2. **Memory.** 2.5 GB resident against 1.36 GB.
3. **Accuracy on this speaker.** 15.9% against `parakeet-unified`'s 8.2% on
   the same five clips.
4. **It still invents text on ten seconds of digital silence** when no
   vocabulary is set, on 1.13.8.

The case for it is real, though, and the corpus replay strengthened it after
these numbers were taken: **Qwen3-ASR is the only candidate that lost no
speech anywhere it was measured**, and the only one that reads the German in
the author's captures. `parakeet-unified`, the model that wins on accuracy,
loses 16 chunks and a fifth of the corpus's words to exactly that
([2026-09-21-parakeet-unified-rnnt.md](2026-09-21-parakeet-unified-rnnt.md)).
So the choice is not "fast and accurate against slow and worse"; it is
whether the author's dictation is English only.

If it is not, reopen this. The patch at
`~/.cache/spokenpad-dev/models/qwen3-asr-family.patch` reapplies to
`config.rs` and `inference.rs` and the configs are at
`~/.cache/spokenpad-dev/models/configs/qwen3-asr*.toml`. Re-measure the speed
on an idle machine first: the number that decides this was taken under load
average 45 and is the weakest part of the case against it.

One detail worth keeping if the family ever lands. sherpa-onnx builds the
prompt by splitting the hotwords on commas, trimming, and joining with
**spaces** — a bare word list, with no framing sentence. The only published
measurement of prompt biasing on technical vocabulary found the framing
matters more than the list. Because the phrases are joined with spaces, a
first vocabulary entry of `Technical terms:` would produce exactly that
framing without any code change. Untested here.
